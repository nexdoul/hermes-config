# JavDB actor → 115 cloud archive

Authoritative contracts — read them before changing anything, and do **not** restate their tables here:

- `/home/hatch/code/javdb/115re/AGENTS.md` — 115 execution layer (primitives, safety invariants, run entry points, state machine, rate limits, verified evidence).
- `/home/hatch/code/javdb/115DailyOrg/AGENTS.md` — daily organizer (fixed phase order, registry, dry-run default).
- `/home/hatch/code/javdb/115DailyOrg/SCHEMA.md` — the shared persistence contract both projects implement.
- `/home/hatch/code/javdb/AGENTS.md` — project-wide rules.

**All 115 execution work happens in `115re/`; all daily organizing happens in `115DailyOrg/`. Never patch `115pan/`** (legacy reference implementation). The two working projects share `_shared/{schema,compat,persistence,lock}.py` — see "Two projects, one schema" below.

There is no database. Persistence is `state.json` (atomic tmp + fsync + rename) plus append-only JSONL (`attempts` / `recovery` / `events`) and the per-batch `snapshot`/`plan`/`result` triple under `runtime/<run>/state/postprocess/`. Local state is only a ledger of intended mutations — the 115 remote snapshot is the source of truth and can rebuild it.

## Two projects, one schema

`115re` (ingest) and `115DailyOrg` (organize) are separate runtimes with **isolated** state — `runtime/<run>/` versus `runtime/dailyorg/`, same root, never shared — but **one data model**. `115DailyOrg/_shared/schema.py` is the single source of truth for field names, normalization and atomic writes; `compat.py` converts a record between the two projects; `persistence.py` and `lock.py` are the reusable store and the single-instance lock.

- **Overlapping movie fields are fixed names**: `movie_url`, `movie_code`, `release_code`, `actresses`, `chinese_title` (plus `movie_title`, `released_date`). DailyOrg's `file_id` / `current_path` / `destination` / `identify_state` / `verified_at` / `duplicate_state` / `organized_root` are **extensions only**, never renames.
- **Change the shared layer in both projects in the same commit**, bump `schema_version`, and ship the migration. A second, incompatible structure is the exact failure this design exists to prevent.
- The `115pan` lifecycle/`run.json` format is not to be reintroduced into either project.

## When to use

- Ingesting an actor from javdb.com into `/我的视频/<演员名>` on the 115 account, or finishing a partial archive.
- Cleaning leftovers: mis-named directories, ad-polluted task directories, duplicate files.
- Proving 断点续传 (crash resume) and idempotent rerun for the 115 execution layer.

This file is the **ingest** class (115re). The **organize** class (115DailyOrg) shares the schema, the wrapper and the safety gates with it, so both live here rather than as two separate skills.

## Preconditions

- Route every 115 call through the wrapper `env/bin/115driver` (SOCKS5 `127.0.0.1:41150` → cnvps, exit `139.224.2.253`). It fails closed by design; the project-root copy is not usable on this host (missing real binary), so always resolve the wrapper under `env/bin/`.
- Use the Hermes venv python for anything importing the project; `PYTHONPATH` must lead with `115re:115re/_internal` (project root goes last, or its stale `javdb_cloud_sync.py` shadows imports).
- Before a long run, confirm stack health: `logs/.stack_healthy` mtime is fresh and both systemd units are active.

## Procedure

Entry points (`$PY` and env per `115re/AGENTS.md` §5):

```bash
cd /home/hatch/code/javdb/115re
$PY run.py --name '<演员>-侦察' --url <actor-url> \
  --target-dir '/我的视频/<演员>' --dry-run --no-ai-title
$PY run.py --name '<演员>-入库' --url <actor-url> \
  --target-dir '/我的视频/<演员>' --apply --no-ai-title --max-pages 5
```

Steps:
1. **Recon the 115 target directory first** and record the baseline: total entries, sub-dirs, files, un-named count, ≤500MB count, same-sha1 groups. The final report must be directly comparable to this baseline.
2. **Dry-run the whole actor**: `run.py --name '<演员>-侦察' --url <actor-url> --target-dir '/我的视频/<演员>' --dry-run --no-ai-title`. Read the plan summary (records / no_task_codes / moves / deletes / renames) before going further, and confirm the run directory is a real name rather than a degenerate slug.
3. **Real run**: same invocation with `--apply`. One active run at a time; never relaunch under a new name to retry — resume always reuses the same `--name`.
4. **Leftovers go through a one-off script under `115re/`**, never hand-typed destructive calls. Order each step so the next is gated on the previous one's verification: move → verify at destination (size **and** sha1) → only then delete. Write a resume branch keyed on the **outcome** (asset already archived), because a crash between move and delete leaves ad-only residue that the fresh-run path reads as "no eligible asset".
5. **Dedupe by sha1 only** (see User preferences).
6. **Verify** with the checklist below, then re-run the identical input to prove idempotence.

## User preferences (standing)

- Same-sha1 duplicates: keep the first, delete the rest; do not escalate — "同 sha1 直接随便保留一个，不好选就直接留第一个".
- A mid-task status ping is a status request, not a stop signal: answer with a compact progress table, then keep executing.
- Different sha1 under one release code is a genuine fork (uncoded vs censored version, or different cuts): preserve both and say so in the report.
- Naming stays `演员名 番号.原扩展名`; an AI title may shorten the middle, but actor name and release code are always assembled by local code.
- Report leftover work items in one plain sentence each, at file level — what the user would see on their drive — with no program state names (`verified`/`failed`) and no error codes. A residual item the user cannot picture is one they cannot act on, and answering 「这两个我看看不懂」 costs a whole turn.
- When the user defers a decision (「留两份」/「我自己看完了自己决定」), touch **no file**: fix the bookkeeping so the program stops erroring and leave both copies on disk for them to choose from. Never park a record as `excluded` to dodge a mismatch that is really a ledger bug — that converts a two-minute journal fix into a permanent mystery entry and sends the user to inspect two healthy files.

## Pitfalls

- **Never dedupe by release code or by a `(2)` filename suffix.** Same-code double files are usually two different releases; deleting by code or suffix loses a real version. Key only on sha1 and *report* same-code/different-sha1 groups untouched.
- **Key every destructive target set on an explicit id whitelist, never on a ledger state field.** `state == excluded` means "stop retrying this", not "the user wants it gone" — a record parked there for an identification problem is a healthy file the user wants kept. Letting a state field into the predicate lets unrelated bookkeeping earlier in the same session silently widen a deletion: a whitelist of 13 became 21 files / 37 GiB against 5.7 GiB approved, and every individual row still read as plausible. Build the id set by hand, abort if any whitelisted id is absent from the ledger, and never let the predicate widen on its own.
- **A dry-run that prints a different volume than the user approved is a failed dry-run.** Compare total file count and bytes against what was actually authorized before going anywhere near `--apply`. The aggregate is the only signal that catches a widened predicate — each row on its own looks reasonable, so a line-by-line review misses it entirely.
- **`115driver rm` answers rc=3 `directory not found` for a path that is already gone — that is the desired end state, not a failure.** Without mapping it, a rerun after a partial delete reports every already-deleted entry as a failure and refuses to settle the ledger, so a fully completed operation looks like a broken run. Treat "not found" as success, and confirm a stale record by listing the parent directory before concluding the file never existed.
- **Prove a deletion landed by full filename and size, never by a release-code substring.** After deleting `TNI-53 (3).mp4`, a grep for `TNI-53` still matches the other versions of that code that were correctly kept, so the audit reports files as "still there" that are in fact gone. Match the exact name and byte size, or diff per `file_id` against the pre-run listing.
- **A registry that relaunches unfinished work makes "stop intentionally" impossible unless the stop is written into the registry itself.** Once a task is registered, the only thing that prevents a relaunch is a state the watchdog treats as terminal, so a deliberate stop has to be expressed as that state (`taskctl stop`) and never as "the process is gone" — a process that merely exited is indistinguishable from one that was killed, and the next tick relaunches it. State this trade-off to the user at registration time as the price of the 已完成 guarantee, not as a footnote.
- **A slug that strips all non-ASCII collapses every CJK run name into one directory** (`run`), silently overwriting another actor's state. Preserve CJK and replace only illegal path characters; after touching the slug function, dry-run under two different CJK names and confirm two distinct run directories.
- **`115driver rm <dir>` requires an explicit `--force` under `--json`.** The failure text (`directory delete requires --force`) reads like the proxy-down error a tunnel hiccup produces in the same window — check for the missing flag before diagnosing the network.
- **`pgrep -f` matches your own command line.** Any pattern you pass that also appears in the shell running the check matches that shell, so a process check reports its own shell as the live run and a cleanup written around the pattern can kill it. Check with `ps -eo args | grep <literal>` instead, or put the pattern in a script file where the checking command line does not contain it. This one bites repeatedly because the failure is silent — the run looks alive.
- **Ad-polluted torrents ship junk directories and spaced-hanzi filenames** (`鮑 魚 直 播 盒 子 …`, `社 區 最 新 情 報.mp4`). Treat spaced-hanzi plus `.html/.mhtml/.url/.txt/.chm/.apk` as junk, and ≤500MB videos with those names as ads — never as the main movie.
- **fastops `apply-plan` can only flatten a directory that is a direct child of the actor root.** A mis-named sibling directory needs path-based `mv` + `rename` + `rm --force`, each verified, not a fastops plan.
- **An "already archived" shortcut must re-verify the archived file** (size >500MB and, when known, sha1 match) before deleting any source directory; refuse on mismatch.
- **A registered directory excludes its whole subtree from a scan, so a file already inside it is never a candidate.** That is what makes organized content safe by construction: a duplicate check can only ever delete the *external* copy, never the organized original. Register directories explicitly, and never infer an actor identity from a directory name.
- **`R115Client.list_dir` returns `RemoteEntry` dataclasses, not dicts.** Feeding them where a mapping is expected yields an empty listing with no error, so a scan reports zero files and looks exactly like an empty account. Convert with `dataclasses.asdict` in the run adapter before any organizer sees them.
- **A wrapper/env root resolver must consider the project root itself, not only `Path.parents`.** `parents` walks upward only, so an `env/` sitting beside the project root is skipped and every 115 call fails closed on a wrapper it never resolved. Resolve env var → project root → parents, in that order.
- **A shared-serializer contract needs both sorted keys and identical normalization on every entry shape.** `canonical_json` without `sort_keys=True` makes the same document serialize to different bytes from different writers, and if `normalize_state_entry` does not normalize `actresses` the way `normalize_movie` does, a migrated document keeps the legacy shape while the two fields disagree about the same film.
- **A cross-project compatibility check compares against the converted record, not the raw input.** A movie record legitimately has no lifecycle field such as `state`, so asserting state-field equality against the input fails on a valid record. Round-trip first, then assert — and assert the round trip is a fixed point, so drift cannot hide in a second conversion.
- **Prove a dry-run was clean by the absence of mutation artifacts, not by reading its summary.** "No mutations were performed" is emitted by the same code path that would have mutated. The evidence is that no `attempts.jsonl` was created and the event journal holds no move/rename/delete entries.
- **Prove a mutating run is real within the first poll, not after it finishes.** Require the artifact only a mutation produces — the log's leading word (`APPLIED`, not `DRY-RUN`) and a grown `attempts.jsonl` — before settling in to wait. A silently dry run costs the whole scan and writes nothing, and the difference is invisible from the tail of a log that looks like progress.
- **Read the plan before going anywhere near `--apply`, and read it out of `state.json`, not the log tail.** The log prints a count line; only the state document carries each file's `current_path`, destination, release code, actresses and `source_parent_path`. Script the dump rather than grepping the log — a f-string with nested quotes is not portable to a one-liner, and `actresses` is a list of dicts, so joining it without the field raises.
- **Read sizes from the right key before calling a plan corrupt.** A plan whose size column prints all zeros usually means the reader used the wrong field: `state.json` per-file documents carry `size_bytes`, and a script reading `size` prints zero for every row while the data is fine. Dump `sorted(f.keys())` for one row first, re-check the threshold story (a real all-zero plan cannot pass the `>500MB` predicate at all), and only then suspect the discover stage. Claiming a corrupt plan that is actually correct costs a full re-run and the user's trust in the report.
- **Same destination path planned for several source files is a rename collision that needs a decision, not a run.** Confirm the sha1 first (identical → keep one, delete the external copies; different → genuine forks, keep both) and never let a rename silently overwrite. Once they are confirmed to be different rips, keep all of them and split the colliding destination names with a numeric suffix — deterministic and keyed on `file_id`, so a resumed run reproduces the same naming.
- **Split the collision names only after the whole batch is planned, and never plan an item twice.** Destination names are unique only in aggregate — three rips of one release code plan the same name three times — so plan everything read-only, resolve collisions, then hand each item to the phases pass marked pre-planned. Planning again there recomputes the original colliding name and discards the suffix: the run reports N renamed items and still writes one destination path. Only a run-level test that counts plan() calls per item catches it, because the collision resolver's own unit tests are correct in isolation.
- **A hand-built test candidate that never reaches plan() looks like a planner bug.** `extract_code` needs the real filename (`f1.mp4` is `no_local_code`) and the main-film predicate needs >500MB, so a synthetic fixture is parked as unresolved/excluded and the destination stays empty. When asserting on `destination_path`, build a plausible film: the code in the name and a real size.
- **A scratch `--state-dir` is not a production state dir**, and the inverse holds too: a probe that runs *against* the production state dir writes to it. A guard verification, a stubbed-driver replay or a "harmless" `dry=False` check lands its rows in the live `attempts.jsonl` / `events.jsonl`, and a later `--resume` reads that noise as real history. Probe against a scratch dir (copy the registry in), or snapshot the whole state dir to `logs/` and truncate only the journals — leaving `state.json` and the registry byte-identical.
- **Global CLI options must precede the subcommand, and the subcommand decides what `--apply` means.** `dailyorg.py discover --state-dir X` is silently ignored because the sub-parser never sees the flag; `dailyorg.py --state-dir X discover` works. And `--apply` is honoured only on the `apply`/`run` subcommands — on `plan` it is a no-op, so `plan --apply` and `apply --resume` (with `--apply` forgotten) both run dry, print `DRY-RUN`, mutate nothing, and burn the whole scan time. This was written once and then hit twice in one session: before launching an apply, grep your own command line for the literal `--apply`, and after launching it, confirm the log's leading word is `APPLIED` and `attempts.jsonl` has grown before you settle in to wait. **No environment variable substitutes for `--apply`**, and a payload that wraps the CLI must assert the mutation itself: `DRY_RUN=0` on the command line does nothing because the organizer reads only the flag, so a wrapper payload ran entirely dry, printed `no mutations were performed`, exited 0, and its task runner wrote the completion marker for a run that changed nothing. Pass the flag explicitly inside the payload and have the payload fail whenever the output contains `no mutations were performed`.
- **A delete guard belongs at *every* exit, and must be exercised at each one.** A single high-level check leaves the low-level helper open: `_cli_rm` was reached directly and deleted a registered directory that `Run.mutate` would have refused. Probe the helper in isolation — assert the refusal *and* that the side-effecting command never fired.
- **Order the guard ahead of the dry-run gate, not behind it.** Behind it, a protected path answers `{"success": True, "dry_run": True}`, which reads as a legitimate request that was skipped and is indistinguishable from success to the caller.
- **`OrganizedRegistry.add()` is in-memory only.** `save_registry(path, registry)` persists it; a guard test that skips the save proves nothing because the guard was never armed.
- **Never assert `success is True` on a `dry=False` mutation in a test** — it shells out to the real cloud driver. Monkeypatch the command runner, then assert the call reached it: that is what distinguishes "allowed" from "refused".
- **Do not report remote-account damage from a stale listing.** Re-list the directory before telling the user what is missing or which operation removed it; the remote state changes between turns.
- **A duplicate-name check must count the names already on the drive, not just the batch.** Three films of one release code all plan the same name, and a sibling that already owns that name on disk is invisible to a batch-only `taken` set — the rename then lands on it. Page the destination (a big actor directory hides names past offset 100) and seed `taken` with everything except the batch's own current names, so a file never collides with itself.
- **A dry-run that persists state downgrades verified films to pending.** The phase list is empty for a verified item, so nothing re-raises it after a read-only pass; the next resume then re-plans work that is already done and a retitle finds nothing to do. Skip the store write whenever `dry` is set — prove it by asserting the writer was never called, not by reading the log.
- **When the same module exists in several copies, append the project root to `sys.path` instead of inserting it at 0.** `javdb_collector.py` lives in `115re/_internal`, `115pan/_internal` and the project root, and only the `115re` copy carries `_http_fetch`; inserting the root first resolves to the copy without it and every import dies into a swallowed empty string. Append it last so it can supply `javdb_cloud_sync` without shadowing the others.
- **An external model/relay answers unreliably, so retry per item rather than once per run.** Measured: the same film and models returned `""` twice and then a correct title on the third call. Bound it (`TITLE_ATTEMPTS`, default 4), retry on a *copy* of the record so the caller's identity never changes, and record the reason for the final failure — a silent empty title is indistinguishable from "no title needed", which is how an entire run finished with no Chinese titles and no error anywhere. **Before blaming the relay's flakiness, check the request's User-Agent**: a relay fronted by Cloudflare refuses a custom UA (`javdb-collector/1.0 (title shortener)`) with `RemoteDisconnected`/`IncompleteRead`, which is an `HTTPException` rather than an `OSError` and so escapes a broad `except OSError` retry loop and surfaces as a per-item transport failure. Copy the browser UA the Hermes providers on this host already send (`extra_headers.User-Agent` in `~/.hermes/config.yaml`) *and* keep the environment's egress proxy — the two are independent requirements, and either one alone still fails. Set the shortener's `max_attempts` above 1 (`3`) so a genuine transient disconnect is retried, then prove it with a 3-record probe before re-running a whole actor. See `references/backfill-retitle.md`.
- **Search the base release code when the suffixed form returns nothing.** JavDB indexes a movie under its base code, so `q=DLDSS-545-UC` searches empty while `q=DLDSS-545` finds it. Fall back to the base code, then keep the suffix the file already carries in the name (identification legitimately returns the short code).
- **Judge "already has a Chinese title" on the file name, not on the recorded field.** A dry-run can persist the title without the rename ever reaching the drive, so a field check skips a file whose name is still title-less. Test the name for the title substring.
- **A title backfill has no source residue — its source *is* its destination.** Seeding it from state gives `source_parent_path` equal to the destination directory, so the ordinary residue path would delete the directory the file was just renamed inside. Make `force_rename` turn residue deletion into a no-op, and assert the mutator was never called.
- **When a user wakes to an apparently empty result, diagnose the host before defending the run.** `uptime` and `who -b` are two commands that separate "the work did not happen" from "the host restarted and took the work with it" — and the user is reading your explanation as one or the other either way. Report the restart as the cause with the evidence, then give the concrete state (how many items, what actually changed on the drive, what is pending, and when it finishes) so the answer is a status report, not an excuse. Also do not read a post-restart failure as a regression: the first cloud call after the stack comes back can fail while the self-heal is still re-establishing the tunnel, so confirm the health marker and `whoami` before concluding anything broke.
- **Force the rename when the actress set is incomplete, not only when the title is.** A name can satisfy the title-less standard check and still be wrong about the cast — a directory an earlier tool filled after only its own actress leaves every co-star missing. Gate on `not all(actress in name for actress in identified_actresses)` in addition to the title check, so a batch naming standards are enforced by the identified cast rather than by whatever the current name happens to contain.
- **Container restarts are an accepted, uncontrollable fact — design for them, and say so plainly.** They wipe detached processes and anything under `/etc`, so a multi-hour chain must be restart-resumable rather than restart-free, and a user who delegated overnight must not have to ask whether anything ran. Never restart the host yourself to make a verification easier.
- **A file name cannot tell you whether it carries a Chinese title.** The actress block is itself Han ideographs, so `江波りゅう AVOP-173.avi` has kanji and no title, and a real title only adds more. A shape filter on the name therefore drops half the untitled files and re-titles half the titled ones. Queue everything and let `plan()` adopt the current name verbatim when the identified title is already in it — no rename phase, no churn.
- **The same trap applies to your own audit, in both directions.** A `[\u4e00-\u9fff]` regex over the whole file name matches the actress names (`榊原萌`, `石川澪`, `鈴木心春` are Han ideographs), so an audit reports every title-less file as titled; and a `good[:3]` sample of the hits reads as confirmation because each shown name legitimately contains kanji. Strip the actress block and the release code out of the name *before* testing, and treat the result as a two-column count rather than a yes/no pass. This audit-vs-reality mismatch is worth more than any single count: the user is comparing your numbers against what they see on screen, and a false "all present" report is read as a claim that their problem does not exist.
- **When a user disputes a number, re-run the measurement before defending it.** They are looking at the drive; you are looking at an earlier count. Re-list the same directory with a corrected criterion, and if your first check was wrong state so in one line and replace the figure — never argue the old one. Replying with a defense of a false-positive check costs a full turn and makes every later number you give less credible.
- **A registered organized directory is excluded from every scan, so a directory an earlier non-DailyOrg run filled has no state to seed a retitle from.** Read it directly: `retitle --registry-dir <dir>` queues every file in it, because the state-seeded path would find zero there.
- **A long backfill run goes through `terminal(background=True)` and is polled with short sleeps.** One film costs one JavDB detail call plus one relay title call, so a 64-file backfill takes 12–25 minutes and writes no log output until the final summary — that silence is the normal shape, not a hang. Do not diagnose a stall from a zero-byte log, and poll with `sleep 60` rather than a multi-minute `sleep`: a long foreground wait that is killed takes the background child with it, losing the run mid-rename.
- **`retitle` has no `--dry-run` flag: read-only is its default.** Passing `--dry-run` errors out with `unrecognized arguments`, and a run without `--apply` prints `DRY-RUN` and mutates nothing. That is the safe direction, but the first real rename *is* the apply — so pilot on a 2–3 name `--names-file` slice, confirm `APPLIED` plus a grown `attempts.jsonl`, then run the rest. The batch summary's `verified` / `pending` / `unresolved` counts carry the diagnosis: `unresolved` means identify never reached the source, `pending` means identified and awaiting rename.
- **A `registry-dir` backfill must pin the destination to the directory it scanned, or the whole batch lands in `default_target`.** `plan()` resolves the destination by matching the *identified actresses* against this project's Registry, and a directory an earlier non-DailyOrg tool filled is not registered there — so the match is empty and the fallback sends every file to `default_target` (`/我的视频`). The symptom is unmistakable once you look at the drive: correctly-titled files sitting in the actor root's *parent*, separator gone (`/我的视频/榊原萌 清纯少女… SONE-772.mp4`). Gate on the candidate's `parent_is_registry` and reuse `parent_path` as `destination_dir`; the directory a file was discovered in is its only correct destination. Recover by moving each file back **by `file_id`**, never by glob — the parent directory holds other actors' files too.
- **`identify` must be told the source host and the proxy.** `d115_identify` hard-coded `https://javdb.com` and called the collector's `_http_fetch` with no `source_proxy`, so every code came back `search_unreachable` even though the same host answers `200` through the krvps tunnel. Make the base URL and the proxy come from the environment with a `source_transport` fallback so `115re` and `115DailyOrg` read one source of truth, and pass `source_proxy` into `_http_fetch` — the collector already learned this, and identify silently did not inherit it.
- **A `200` with an empty `content` is a reasoning model, not a transport failure.** `step-3.7-flash` puts the whole answer in `reasoning` / `reasoning_content` when `max_tokens` is small (measured: `max_tokens:100` → `"content":""` every time; `300` → the title). Read those fields as a fallback and raise `max_tokens`; a per-item retry ladder alone never fixes it, because every attempt looks like a valid empty answer. This is how a whole actor's run finished with `failures: 191` and no error anywhere — reported as success with zero titles.
- **A probe directory the run itself creates is not a directory to count.** A diagnostic run named `probe-route` creates `/我的视频/probe-route` on the real account. List the root before trusting a count and treat unexpected directories there as your own residue.
- **Verify a partially-applied backfill by diffing the listing against the pre-run listing, not by counting.** A directory whose first N entries are already renamed looks finished; the remaining title-less files sit further down. Relist, compare per `file_id`, and report `unchanged / renamed / missing` before deciding what to re-run.
- **A proxy-node sweep is the last probe before rotation is abandoned, and one full sweep is enough.** The user's first proposal for an IP block is usually subscription-node rotation, which is worth exactly one honest test — parse the subscription, filter the pseudo-nodes, wire `url-test`, sweep every node. When the control hosts return 200 on those same nodes while the target refuses all of them, the block is on the provider's address range and no further node is going to answer: say so plainly with the pool count, restore the config, and stop. Re-running the sweep hoping for a different pool burns the round and recycles a settled question. **Make the sweep honest before believing its count**: read the group's `now` back after each switch (a `204` can leave the group on the previous node) and drop iterations that did not move, and judge each response by a content marker the target alone emits — a Cloudflare refusal page carries `<title>` and `<!DOCTYPE html>` too, so a markup grep manufactures a healthy node count. An N-times-the-same-node sweep and a genuinely blocked pool look identical from the outside. See `references/backfill-retitle.md` and the rotation triage in `vps-egress-routing`.
- **Exhaust the routes the user names, in the order they name them, before declaring a source unavailable.** An instruction like "依次尝试" is a work order, not background: each named option is executed and reported on its own result, and a dead end is only declared after every option has been run. A route that fails structurally is reported as "this mechanism cannot work here" with the evidence that rules it out — not folded into a general "the target is blocking us". This host's egress cannot carry an application's HTTP request onto a VPS network no matter how the proxy variables are set (see the tunnel-direction fact in `vps-egress-routing`), so the working shape for a JavDB source is running the fetch *on* the VPS over SSH and keeping this host as dispatcher.
- **The reachable JavDB source is `javdb580.com` from a VPS exit, not `javdb.com`.** From that exit `javdb.com` answers Cloudflare `451` with `error code: 1026` (a legal/region policy, not an IP block) while `javdb580.com` answers `200` with a full page and a working search endpoint — the two carry the same database. Before reporting the source unavailable, try the sibling domain on the exit you *can* reach, and check the cookie/redirect handling still matches the new host.
- **Judge self-heal probe failures by retry count, not by the first failure.** A network probe that flakes intermittently makes a 5-minute self-heal cron emit an alert on every flake even though the next pass succeeds. Retry inside the script (3 attempts with a short backoff), log single failures as `WARN`, and only fail the run when every attempt fails. The same reasoning applies to any periodic health check: a single-sample check turns normal jitter into recurring alerts.
- **Separate the fault the self-heal owns from the fault it cannot touch, before choosing the exit code.** The job of a stack self-heal is repairing its own units, tunnels and proxies; a third party refusing this host's IP is not repairable by any script. Classify with one cheap independent probe taken beside the failing one — a bare `curl` to the third-party host next to `google.com` and `github.com` (both 200 while the target answered 403 `Attention Required! | Cloudflare`) proves the host's egress is fine and the block is external. Then report the owned half as healthy and the blocked half as `DEGRADED` with `exit 0`, and never touch the health marker so it keeps meaning "last round everything was green". Exiting 1 on an unfixable external fault turns a status line into an alert every round and hides that everything the script *does* own is fine.
- **When a probe is more expensive than the cron interval, remember its conclusion instead of redoing it.** Three 150-second route attempts cost more than a single 5-minute round, and an IP block cannot lift inside that window, so every round pays full price for the same answer. Write a cooldown stamp on confirmed external block and have later rounds do one fast probe; clear the stamp and resume the full path the moment the fast probe succeeds. This cuts a round from 2m40s to ~4s and needs no manual cleanup when the block lifts.
- **Read the self-heal's own stage log before editing the script.** A cron alert carries only an exit code; the log's per-stage `WARN`/`ERROR` lines localize the failing stage and mark the earlier stages (units, ports, `whoami`) as known-good. That is what distinguishes "the script is broken" from "an external dependency is down", and the two demand opposite responses.
- **Validate every actor URL before planning an ingest.** An uncensored (`無碼`) actress page can be login-gated — it answers 302 to `/login`, and the collector reports an empty source for a URL that looks live in a browser. Probe the URL through the collector first; if it comes back empty, search `q=<actress name>&f=actor` and pick a working entry (often an alias hub that aggregates several of that actress's names, so it yields the most films), then tell the user which identity the directory will actually cover — a hub covers more films than the single name they asked for.
- **A verify failure on a file that needed no rename is a probe hiccup, not lost work.** When the identified cast and title are already in the name, `plan()` adopts it verbatim and there is nothing to mutate — but the verify that follows still reads the drive and can fail on one flaky listing, marking the item `failed`. Check whether the name already carried the full cast before treating `failed` as a mutation failure, and note that `failed` is still finished for resume purposes, so a re-run will not redo it.
- **A batch that persists only after the whole pass has a loss window equal to the whole pass.** Identify is one network call per film and the state document is written after the last item, so a single 377-file batch loses ~45 minutes to any interruption — and a run killed mid-identify leaves zero drive changes and a zero-byte log, which reads as "nothing ran". Slice the work into bounded batches off a frozen name list (`--names-file` / `--limit`), let `filter_resumable` skip finished items, and re-run the driver from the top after any interruption.
- **A detached driver does not survive a container restart, so a multi-hour chain needs a cron relauncher.** `setsid` protects a background job from gateway-level signals only; a platform-initiated restart still takes it, and the user who went to sleep wakes to an apparently empty result while the state on disk says otherwise. Chain the jobs behind marker files, add a rate-limited watchdog cron that relaunches whichever driver is missing, and make every driver idempotent at the top so a relaunch can never duplicate work. See `references/long-run-resilience.md`.
- **A watchdog that short-circuits on a fixed set of "done" markers is permanently deaf to every task it was not written for.** The completion gate runs before anything else, so once those markers exist the watchdog logs `nothing to do` on every tick and relaunches nothing — and because it still fires and its stamp still advances, it reads as perfectly healthy while a newer task sits dead. Complete-and-healthy are indistinguishable from the outside, so gate each task on its own completion condition read from a registry and let the recovery question be "is there registered work that is not done", never "are these two specific markers present". See `references/long-run-resilience.md`.
- **An empty paged listing is the end of the directory, not a failure — and page fullness is never proof of a next page.** `--limit 100 --offset 100` on a 61-entry directory answers `files: 0` with `success: true`. Drive every walk from the response's own `has_more` / `next_offset`, treat `has_more: false` as final even on a full page, and fall back to page fullness only when a response omits both. A bulk failure shaped like "every record failed, every file is on the drive as planned" is this bug, not lost work. See `references/daily-organizer.md` for the full contract, the decisive probe, and the full-set re-verification.
- **A `verified` relabel that does not re-read the drive is a lie.** Restoring ledger state from a stale snapshot fabricates provenance — the journal ends up asserting a check nobody ran. Any reconciliation script must re-list the live directory for every record it touches, and must be auditable for what it *cannot* do: grep the module body for `subprocess`, `shutil`, `remove`, `rename` and confirm the only write is the state document, then show the user that. Prefer one big `--limit` read per directory over a per-file read (`--limit 1150` returns 379 entries against one 300-entry directory).
- **Before reconciling a ledger, check whether the record lives in the state dir the tool itself shares.** A payload run against a production `--state-dir` rewrites the counts, the run name and the timestamps in `state.json`, so the numbers you are about to "fix" may have moved since you read them. Re-read the document immediately before the reconciliation and reconcile the set that is actually there, not the set you remember.
- **A `(N)` suffix is the drive's marker that another file already owns the name — so a per-code ledger record must be keyed on the physical file, never on the target name.** Two records for one release code can both carry the same `target_name` while pointing at two different `file_id`s and two different sizes; matching on the name then makes one of them permanently unfixable. Match on size (and the file id), and treat the name as descriptive only.
- **115 writes its duplicate suffix with no space: `SW-944(1).mp4`, not `SW-944 (1).mp4`.** A matching regex written from the OS convention (` (N).`) matches nothing on this drive, so every lookup fails and the entries look lost. Build the candidate name out of the real name read from the listing and confirm with `re.match` against that constructed string — never against a CJK string you retyped in a shell, where the two strings silently differ and the false negative gets blamed on the regex.
- **Write and run journal fixes as importable scripts, not `python -c` one-liners.** A one-liner puts a CJK filename and a regex in the same shell-quoted line; the shell re-escapes it, so a pattern that is provably correct when imported fails when typed, and you burn turns auditing a correct regex. Load the module with `importlib` and call the function directly — that also gives the real data instead of a retyped sample.
- **Group the ledger's failure reasons before believing "the run was interrupted."** A killed run and a deterministic code fault produce the same outside picture — process gone, work incomplete — so `Counter(f['last_error'] for f in state.json['files'] if f['state']=='failed')` is the first diagnostic, not the last. One reason covering ~all records (272 of 272 here) is a systematic fault that a relauncher will only repeat on every tick; only a spread of reasons, or none at all, is consistent with an interruption. Do this check *before* registering a task for auto-relaunch, because automating an unhealed bug converts one failure into a recurring one and burns the provider's rate budget until attempts exhaust. Same rule as a diagnosis before a fix: `references/long-run-resilience.md` and `references/daily-organizer.md` carry it for each context.
- **Read a state directory from the script that owns it, not from a project note.** `grep -n '<VAR>=' <script>.sh` prints the root the code actually uses; a documented path that was never wired reads as an empty registry, and you report "nothing is running" for work that is alive elsewhere. Paths in notes drift from the code that implements them.
- **A task registry is not the set of everything running, so "nothing unfinished" and "there is traffic" can both be true.** When asked which heartbeat has not finished, report the registry's terminal states — then answer the observed traffic from the process table and `/proc/<pid>/environ`, naming the owning systemd unit, because an independently installed service is in no registry and no Hermes cron. Check the connection list for the target the user actually named before attributing traffic to any of them. Audit procedure in `references/long-run-resilience.md`.

## Verification checklist (always report these numbers)

- **Prove a dry-run was clean by the absence of mutation artifacts, not by reading its summary.** "No mutations were performed" is emitted by the same code path that would have mutated. The evidence is that no `attempts.jsonl` was created and the event journal holds no move/rename/delete entries.
- **Prove a mutating run is real within the first poll, not after it finishes.** Require the artifact only a mutation produces — the log's leading word (`APPLIED`, not `DRY-RUN`) and a grown `attempts.jsonl` — before settling in to wait. A silently dry run costs the whole scan and writes nothing, and the difference is invisible from the tail of a log that looks like progress.
- **Read the plan before going anywhere near `--apply`, and read it out of `state.json`, not the log tail.** The log prints a count line; only the state document carries each file's `current_path`, destination, release code, actresses and `source_parent_path`. Script the dump rather than grepping the log — a f-string with nested quotes is not portable to a one-liner, and `actresses` is a list of dicts, so `", ".join(actresses)` raises.
- **Read sizes from the right key before calling a plan corrupt.** A plan whose size column prints all zeros usually means the reader used the wrong field: `state.json` per-file documents carry `size_bytes`, and a script reading `size` prints zero for every row while the data is fine. Dump `sorted(f.keys())` for one row first, re-check the threshold story (a real all-zero plan cannot pass the `>500MB` predicate at all), and only then suspect the discover stage. Claiming a corrupt plan that is actually correct costs a full re-run and the user's trust in the report.
- **Same destination path planned for several source files is a rename collision that needs a decision, not a run.** Confirm the sha1 first (identical → keep one, delete the external copies; different → genuine forks, keep both) and never let a rename silently overwrite. Once they are confirmed to be different rips, keep all of them and split the colliding destination names with a numeric suffix — deterministic and keyed on `file_id`, so a resumed run reproduces the same naming.
- **Split the collision names only after the whole batch is planned, and never plan an item twice.** Destination names are unique only in aggregate — three rips of one release code plan the same name three times — so plan everything read-only, resolve collisions, then hand each item to the phases pass marked pre-planned. Planning again there recomputes the original colliding name and discards the suffix: the run reports N renamed items and still writes one destination path. Only a run-level test that counts plan() calls per item catches it, because the collision resolver's own unit tests are correct in isolation.
- **A hand-built test candidate that never reaches plan() looks like a planner bug.** `extract_code` needs the real filename (`f1.mp4` is `no_local_code`) and the main-film predicate needs >500MB, so a synthetic fixture is parked as unresolved/excluded and the destination stays empty. When asserting on `destination_path`, build a plausible film: the code in the name and a real size.
- **A scratch `--state-dir` is not a production state dir**, and the inverse holds too: a probe that runs *against* the production state dir writes to it. A guard verification, a stubbed-driver replay or a "harmless" `dry=False` check lands its rows in the live `attempts.jsonl` / `events.jsonl`, and a later `--resume` reads that noise as real history. Probe against a scratch dir (copy the registry in), or snapshot the whole state dir to `logs/` and truncate only the journals — leaving `state.json` and the registry byte-identical.
- **Global CLI options must precede the subcommand, and the subcommand decides what `--apply` means.** `dailyorg.py discover --state-dir X` is silently ignored because the sub-parser never sees the flag; `dailyorg.py --state-dir X discover` works. And `--apply` is honoured only on the `apply`/`run` subcommands — on `plan` it is a no-op, so `plan --apply` and `apply --resume` (with `--apply` forgotten) both run dry, print `DRY-RUN`, mutate nothing, and burn the whole scan time. This was written once and then hit twice in one session: before launching an apply, grep your own command line for the literal `--apply`, and after launching it, confirm the log's leading word is `APPLIED` and `attempts.jsonl` has grown before you settle in to wait. **No environment variable substitutes for `--apply`**, and a payload that wraps the CLI must assert the mutation itself: `DRY_RUN=0` on the command line does nothing because the organizer reads only the flag, so a wrapper payload ran entirely dry, printed `no mutations were performed`, exited 0, and its task runner wrote the completion marker for a run that changed nothing. Pass the flag explicitly inside the payload and have the payload fail whenever the output contains `no mutations were performed`.
- **A delete guard belongs at *every* exit, and must be exercised at each one.** A single high-level check leaves the low-level helper open: `_cli_rm` was reached directly and deleted a registered directory that `Run.mutate` would have refused. Probe the helper in isolation — assert the refusal *and* that the side-effecting command never fired.
- **Order the guard ahead of the dry-run gate, not behind it.** Behind it, a protected path answers `{"success": True, "dry_run": True}`, which reads as a legitimate request that was skipped and is indistinguishable from success to the caller.
- **`OrganizedRegistry.add()` is in-memory only.** `save_registry(path, registry)` persists it; a guard test that skips the save proves nothing because the guard was never armed.
- **Never assert `success is True` on a `dry=False` mutation in a test** — it shells out to the real cloud driver. Monkeypatch the command runner, then assert the call reached it: that is what distinguishes "allowed" from "refused".
- **Do not report remote-account damage from a stale listing.** Re-list the directory before telling the user what is missing or which operation removed it; the remote state changes between turns.
- **A duplicate-name check must count the names already on the drive, not just the batch.** Three films of one release code all plan the same name, and a sibling that already owns that name on disk is invisible to a batch-only `taken` set — the rename then lands on it. Page the destination (a big actor directory hides names past offset 100) and seed `taken` with everything except the batch's own current names, so a file never collides with itself.
- **A dry-run that persists state downgrades verified films to pending.** The phase list is empty for a verified item, so nothing re-raises it after a read-only pass; the next resume then re-plans work that is already done and a retitle finds nothing to do. Skip the store write whenever `dry` is set — prove it by asserting the writer was never called, not by reading the log.
- **When the same module exists in several copies, append the project root to `sys.path` instead of inserting it at 0.** `javdb_collector.py` lives in `115re/_internal`, `115pan/_internal` and the project root, and only the `115re` copy carries `_http_fetch`; inserting the root first resolves to the copy without it and every import dies into a swallowed `""`. Append it last so it can supply `javdb_cloud_sync` without shadowing the others.
- **Search the base release code when the suffixed form returns nothing.** JavDB indexes a movie under its base code, so `q=DLDSS-545-UC` searches empty while `q=DLDSS-545` finds it. Fall back to the base code, then keep the suffix the file already carries in the name (identification legitimately returns the short code).
- **Judge "already has a Chinese title" on the file name, not on the recorded field.** A dry-run can persist the title without the rename ever reaching the drive, so a field check skips a file whose name is still title-less. Test the name for the title substring.
- **A title backfill has no source residue — its source *is* its destination.** Seeding it from state gives `source_parent_path` equal to the destination directory, so the ordinary residue path would delete the directory the file was just renamed inside. Make `force_rename` turn residue deletion into a no-op, and assert the mutator was never called.
- **When a user wakes to an apparently empty result, diagnose the host before defending the run.** `uptime` and `who -b` are two commands that separate "the work did not happen" from "the host restarted and took the work with it" — and the user is reading your explanation as one or the other either way. Report the restart as the cause with the evidence, then give the concrete state (how many items, what actually changed on the drive, what is pending, and when it finishes) so the answer is a status report, not an excuse. Also do not read a post-restart failure as a regression: the first cloud call after the stack comes back can fail while the self-heal is still re-establishing the tunnel, so confirm the health marker and `whoami` before concluding anything broke.
- **Force the rename when the actress set is incomplete, not only when the title is.** A name can satisfy the title-less standard check and still be wrong about the cast — a directory an earlier tool filled after only its own actress leaves every co-star missing. Gate on `not all(actress in name for actress in identified_actresses)` in addition to the title check, so a batch naming standards are enforced by the identified cast rather than by whatever the current name happens to contain.
- **Container restarts are an accepted, uncontrollable fact — design for them, and say so plainly.** They wipe detached processes and anything under `/etc`, so a multi-hour chain must be restart-resumable rather than restart-free, and a user who delegated overnight must not have to ask whether anything ran. Never restart the host yourself to make a verification easier.

- Actor root: sub-dirs left (target 0, or only documented-ambiguous), un-named files (0), files ≤500MB (0), same-sha1 duplicate groups (0), total files, distinct release codes.
- Idempotent rerun: converges in seconds, `batches: []`, `attempts.jsonl` line count unchanged, offline task count unchanged, file list unchanged.
- Evidence retained under `runtime/<run名>/` (`report.json`, `state/`, `attempts.jsonl`, `state/postprocess/*/plan.json`).
- `115re/tests` green via the Hermes venv python (the project's own `./venv` cannot run the suite).

See `references/daily-organizer.md` for the `115DailyOrg` procedure — fixed phase order, registry, identification, duplicate rules, CLI, smoke checklist and the systemd schedule. It shares this file's 115 wrapper, safety gates and persistence model, so apply the pitfalls above there too.

See `references/long-run-resilience.md` when a job is expected to run unattended for hours — the restart-proof chain, the honest resume report, and the duration you owe the user up front.
