# Cross-Surface Feature Engineering

Use this workflow when a behavior is reached through multiple entry points—such as a CLI and a messaging gateway—or depends on shared state across components. Focus on mapping and proving the complete behavior path; follow the repository's own contributor rules and test commands.

## When to Use

- A feature or fix must behave consistently across multiple application surfaces.
- A command travels through parsing, registration, dispatch, state changes, and execution.
- One-shot or deferred behavior crosses turns, sessions, or async confirmation flows.

## Procedure

1. **Load local guidance first.** Read applicable project `AGENTS.md` files and contributor guide. For Hermes runtime changes, load the `hermes-agent` skill and slash-command/contributor references; consult live docs/source when references are incomplete.
2. **Map paths before editing.** Search command registration, parser, dispatch, surface handlers, shared state, busy/idle behavior, confirmation callbacks, and analogous tests. Trace the actual routed component rather than assuming an existing generic component is mounted. Audit configuration load/save normalization, launch-time rewriting, GET-triggered provisioning, and restart-time auto-resume: each can alter behavior without the user pressing start. Identify independent paths explicitly. Completion: every user-facing entry point and deferred state transition is mapped.
3. **Write the behavioral matrix.** Cover valid/malformed input, unknown selector, success, setup failure (payload must not execute), restoration/cleanup, and confirmation/cancellation. For temporary state, specify ownership key and lifecycle. For localization, include selected-language behavior, English fallback/parity, interpolation placeholders, and the same string on each independently rendered surface. When hard-coded adapter/surface wording must become language-dependent, follow `references/localizing-adapter-text.md` (words vs markup, import-time constants, per-adapter label overrides, number/unit splitting).
4. **Establish the test loop.** Find the repository's documented test runner and focused invocation; confirm the environment can execute it, including async plugins and per-file sharding. Build one end-to-end vertical slice at a time: regression test, observe expected failure, minimal route, focused test. Then proceed to the next surface/branch. Avoid batching speculative changes across registration, dispatch, async state, and tests. A failing test only counts as a RED when it ran and asserted wrongly — see `references/red-validity.md` before writing any production code.
5. **Patch narrowly from fresh source.** Read the complete target function and nearby callers immediately before editing. Use unique context. After each edit, inspect the changed function/diff and run the focused behavior test before proceeding.
6. **Check interface blast radius.** Before changing shared helper signatures/contracts, search production callers and test fixtures/mocks; update each consumer deliberately.
7. **Verify integration paths.** Run focused tests for each surface and state transition, then the repository's appropriate regression suite. For provider configuration, verify the credential with a live model call, read back the saved configuration, then exercise the actual UI's provider discovery, existing-record editing, and enabled-state display; these are independent acceptance gates. An API save does not prove the browser offers that provider. Keep configuration tests separate from execution: do not start trading or other autonomous side effects merely to prove a model connection. For exchange integrations, inspect client construction and initialization before any authenticated balance probe; a GET handler can instantiate a client that POSTs account-mode changes. Verify a genuinely read-only probe, identify the queried account and product, and report authentication, funding, and order capability separately; a successful zero-balance response is not an invalid credential or proof of trading readiness. Follow `references/exchange-connection-verification.md` for these gates. Review for omitted routes, leaked temporary state, accidental persistence, and unrelated edits.
8. **Report evidence precisely.** List what changed, commands actually run, results, and remaining gaps. Syntax/lint/source inspection are not behavior-test passes. If the runner cannot execute, report that blocker plainly. When the user reports a regression after deployment, revoke the affected success claim: distinguish what remains verified from the newly failing interaction, even if the user elects not to fix an optional feature.

## Pitfalls

- **Provider discovery and saving must share one catalog.** When the public supported-provider endpoint omits a still-supported compatible provider, merge explicit compatible templates with configured records (configured IDs/details win) in both the picker and its save handler; adding a picker alone leaves new-provider saves rejected as unknown. Test stored-key blank preservation separately from new-key validation.
- **Fix overlay lifetime without disabling its intended action.** Keep global connection panels closed by default, close them on route changes, support outside/Escape dismissal, and keep stacking below configuration dialogs. Test both absence of unwanted overlays and the positive path: explicitly opening the panel must still expose usable controls. Watch for outside-click handlers closing the panel on its own trigger event. Component tests and a deployed bundle hash do not prove real wallet interaction; report that path as unverified until exercised without signing or spending. If the user says the optional integration is unnecessary and asks to leave it alone, stop repairing it rather than expanding scope.
- **Static frontend hot deployments need image persistence.** For an unmounted nginx document root, copy the tested build into the running container without restarting, then also bake that exact dist into the compose image tag. Preserve prior image/static assets and verify identical hashes across public URL, running container, and saved image; unchanged container start time/restart count proves no restart.

- **Assuming one handler covers every surface.** CLI/TUI, Gateway idle, and Gateway busy dispatch may be independent; trace each path. The same holds for human confirmation: a tool call issued from your own local shell carries no approval callback, so no prompt is presented at all and the call returns immediately through the local scanner. To observe the real card, issue the request through the surface the user actually sees.
- **Forwarding after a failed transition.** Verify authoritative per-session/per-turn state before payload execution; restore original input and stop on setup failure.
- **Losing deferred work in confirmation flows.** Associate original payload and selector with the exact session until success or cancellation; don't consume state before knowing the callback outcome.
- **Patching partial/repeated source context.** Truncated excerpts and repeated snippets can target the wrong block; inspect the complete function and diff immediately.
- **Wiring a call to a helper you have not confirmed exists.** A cross-session notifier reached for an adapter lookup plus a `_chat_id_for_session`-style resolver the gateway never defines, so its send path had no live target. Confirm every external symbol with `grep -n 'def <name>' gateway/*.py` before writing the call, and prefer the runtime's own resolution path (`_delivery_adapter_for(source)` for an in-turn surface, `_inject_watch_notification` for a synthetic cross-session event) over inventing a second router.
- **Testing only a helper.** Parser tests do not prove discovery, routing, session identity, execution, or cleanup; exercise each surface boundary.
- **Confusing request-level retry control with page-level retry control.** Map component mount effects, polling, cache revalidation, route changes, and sibling consumers of a shared provider; each can initiate fresh requests after a helper correctly stops its own retries. Test request counts at the page boundary with mocked failures, not only inside the transport helper.
- **Treating optional-provider failure as whole-page failure.** Correlate failing request URLs with the widget that consumes them and inspect shared error interceptors; healthy core APIs can coexist with a failed paid widget that emits a global server-error toast. Define independent acceptance gates for core page use, optional data availability, and localized failure handling. For paid providers, use mocked render/failure tests unless spending is explicitly authorized; never represent missing provider data as fabricated signals or call a green health endpoint proof of page recovery.
- **Calling static checks feature verification.** Compilation catches syntax, not lifecycle or dispatch defects; distinguish evidence types in the final report.
- **Making the English baseline depend on environment defaults.** When adding localized strings, select English explicitly for the English branch and preserve the original English copy; this keeps tests deterministic and prevents config/environment locale from leaking into fallback text.
- **Editing every locale just to satisfy catalog parity.** Add every key with correct placeholders, but do not represent copied English text as completed translation; scope translation claims to locales actually reviewed.
- **Testing async suites without the project's async plugin.** Check runner and plugin availability first, because pytest can collect async tests yet report them unsupported rather than execute them.
- **Claiming a locale change is live before the process restart.** Python modules and locale catalogs are loaded and cached in-process at start, so neither a catalog edit nor source takes effect until the gateway restarts. Language resolution is per-call, so no new conversation is needed — say plainly that the change is on disk and pending restart, and separate "code changed" from "user-visible".
- **Asserting your change broke failures you cannot run.** When a suite is unrunnable for an environmental reason, count the failure messages: run the tests, grep the specific environmental error (e.g. "async def functions are not natively supported"), and compare that count to the failure total. A 1:1 match is evidence the failures are pre-existing; a mismatch means find the real cause before proceeding.
- **Reading a config key's commented-out line as its value.** A commented key means the code default applies, which is often a different value than the one in the comment. Resolve the effective value from the reader's default before diagnosing behavior that depends on it.
- **Changing exact-output assertions to accept translations without reviewing expected semantics.** Update assertions narrowly for intentional locale variants; broad OR clauses can hide wrong or missing acknowledgement text.
- **Assuming the base class output is what an adapter emits.** Adapter class bodies format markup around shared English constants at import time, so a class attribute cannot see the active language — localize in the render path, and render each real adapter under both languages to see what actually ships.
- **Assuming phrase replacement covers a shorter adapter label.** A label that is not a superstring of the shared English phrase (`"✅ Session"` vs `"Allow Session"`) silently no-ops; verify by reading the rendered button row, not the dict.
- **Letting an English number/unit formatter feed a translated sentence.** Expose count and unit separately in the catalog and reassemble per language, or the target language leaks English units.
- **Treating an en == zh catalog value as an untranslated key.** Status labels, pure interpolation templates, input-recognizer strings, and internal style identifiers are language-neutral; diff the values before claiming translation coverage.
- **Proving a path was reached before tuning the gate.** If the target surface's log contains no trace of the request, the request never entered that surface, and no change to the gate can move it. Verify arrival first (a log line, or the transport's resolved-record count), then adjust policy or payload.
- **Writing an operator policy that cancels the gate.** Operator-supplied policy text is appended to the reviewer prompt as trusted input, so a sentence in it can invert the reviewer's own default — a "when uncertain, prefer to allow" line silences "escalate when uncertain". List only the narrow escalate/approve cases and explicitly restate the default behavior for everything uncovered.
- **Accepting a RED that never ran.** A compile error, unresolved import, or undefined symbol is a build failure, not evidence about behavior — the test must load, execute the code under test, and assert wrongly. Scaffold a deliberately-wrong module or the bare missing field/signature to get past it, and re-run before writing production logic. Record the failing run to a log beside the GREEN log; a suite only ever seen passing has never been validated.
- **Reading an immediate PASS as a GREEN.** A test written before its feature that passes on the first run is not exercising the path you think: an earlier guard returned first and the assertion only checked `err != nil`, a mock absorbed the branch, or the assertion is over-broad. Put call/record counters on the mock and assert the specific error plus the absence of the side effect; a broad `toBeTruthy()` hides the wrong branch.
- **Implementing before watching the RED.** If production code was applied first, the cycle is void: revert it, capture the real failing run, then re-apply. Committing without a recorded RED leaves the test unvalidated for the whole life of the feature.
- **Discovering untestability mid-RED and refactoring for testability as a side note.** When the code under test calls a package-level fetch directly, add the indirection (`var LoadThing = Fetch`, or `export const loadThing = fetchThing`) with the production default unchanged, and describe it in the commit as a testability seam rather than new behavior.
- **Reading "the command returned" as "the prompt was shown."** A late click on an expired prompt resolves zero records and looks identical to a prompt that never existed; confirm the interactive path carried the prompt with the transport's resolved-record count before declaring the flow works.
- **Building workarounds around a bug the user reports as fixed.** When an incident is resolved, drop the defensive branch and keep the normal implementation path — workarounds for dead bugs become permanent complexity and a second behavior to test.
